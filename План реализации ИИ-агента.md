# План реализации ИИ-агента для базы знаний ТГК

> Статус: только план. Разработка начнётся в новой сессии после одобрения.
> Исходный документ: `Пожелания к приложению для базы знаний.md`
> Учёт замечаний независимого аудита: устранены декларативность, внутренние противоречия, добавлена модель данных, надёжность конвейера, дайджест, критерии качества и безопасность.

## 0. Этап 0. Уточнение scope и инвентаризация (до кодирования)

**Цель:** зафиксировать границы проекта, источники MVP, схему данных и судьбу существующих скриптов, прежде чем писать код.

**Задачи:**
1. Подтвердить локальный однопользовательский режим.
2. Определить, требуется ли поиск **новых внешних материалов вне заданного списка** (по Пожеланиям — нет, источники выбирает человек).
3. Выбрать 1–2 приоритетных источника для MVP (например, Telegram + YouTube).
4. Выбрать один проверенный LLM-провайдер для MVP (остальные — после проверки совместимости).
5. Описать, какие существующие скрипты в `scripts/` сохраняются, оборачиваются или заменяются (один поток, не два параллельных конвейера).
6. Утвердить минимальную схему данных: заметка, профиль, источник, элемент очереди (см. Раздел 3.1).
7. Подготовить небольшой набор материалов и типовых вопросов для проверки качества поиска и суммаризации.
8. Задача: проверить наличие и корректность файла `LICENSE` (MIT, правообладатель, совместимость зависимостей).

**Критерии готовности Этапа 0:**
- Документировано, какие скрипты остаются, какие оборачиваются, какие удаляются.
- Определены 1–2 источника MVP и один LLM-провайдер.
- Утверждена схема данных (таблицы и поля SQLite, YAML-файлы).

## 1. Стек технологий и фреймворки

Минимальный, легковесный стек.

| Компонент | Технология | Обоснование |
|-----------|-----------|-------------|
| Язык программирования | **Python 3.10+** | Соответствует существующим скриптам, встроенный `sqlite3` с FTS5 |
| Конфигурация и валидация | **Pydantic v2** | Типизированные настройки, встроенная загрузка `.env` через `pydantic-settings` |
| CLI-интерфейс | **Typer** (на базе Click) + **Rich** | Интерактивные опросы (интервью), таблицы, цветной вывод, флаг `--json` |
| Планировщик задач | **cron** (внешний) | Сбор и напоминания по расписанию через крон; встроенный APScheduler не нужен |
| Локальное хранилище состояния | **SQLite** (`sqlite3`, встроенный) | Очередь, FTS5-индекс заметок, граф связей `note_links`, обратная связь, история промптов — без внешней БД |
| Формат знаний | **Markdown + YAML frontmatter** | Формат Obsidian, совместим с существующими заметками |
| Шаблоны промптов | **Отдельные task-specific промпты** (общий блок принципов + промпты по задачам) | Суммаризация, отбор релевантности, ответ на вопрос, актуализация, инсайты — разные задачи |
| HTTP-клиент для LLM (фон) | **httpx** | Один универсальный клиент к OpenAI-совместимому API (один проверенный провайдер для MVP) |
| Тестирование | **pytest** | Юнит- и интеграционные тесты |
| Линтинг и форматирование | **ruff** | Линтинг, проверка импортов, форматирование в одном инструменте |
| Сборка/установка | **pyproject.toml** (setuptools) | Установка пакета `kb-agent` |

**Не используются:** `python-dotenv`, `loguru`, `mypy`, `APScheduler`, `Jinja2`, `pytest-asyncio`, шесть отдельных HTTP-адаптеров агентов, микросервисы, внешняя БД, векторная БД, веб-интерфейс.

## 2. Общая архитектура системы

Система разделена на **внутренний конвейер обработки** (фоновой режим через cron) и **внешний интерфейс для ИИ-агентов** (MCP + CLI JSON). Существующие скрипты в `scripts/` остаются поставщиком сырых данных, а `kb_agent/` реализует интеллектуальный слой.

### Разделение ролей

| Роль | Кто выполняет | Как реализовано |
|------|---------------|-----------------|
| Фоновая суммаризация новых постов | Внутренний `KnowledgeAgent` | Один `LLMClient` + task-specific промпты |
| Доступ внешних агентов (Hermes, Cursor, ClaudeCode, OpenCode, OpenClaw, Kimi Claw) к БЗ | Внешние агенты сами вызывают приложение | **MCP-сервер** `kb-agent mcp-serve` + CLI `--json` + `SKILL.md` / `.cursor/mcp.json` |
| Поиск и ответы на вопросы человека | Внутренний конвейер + `kb-agent ask` | `SQLite FTS5` + контекстная суммаризация |

### Высокоуровневая схема

## 3. Детальное описание компонентов

### 3.1. Модель данных и схемы

**Единая схема элементов:**

| Сущность | Хранилище | Ключевые поля |
|----------|-----------|---------------|
| Источник (`source`) | `sources.yaml` (конфиг) | `id`, `type` (telegram/youtube/website/personal/papers/social), `url`, `enabled`, `last_checked`, `last_updated` |
| Элемент очереди (`raw_queue`) | SQLite | `id`, `source_id`, `external_id`, `canonical_url`, `title`, `raw_text`, `raw_hash`, `received_at`, `state` (`new`/`processing`/`processed`/`skipped`/`failed`), `attempts`, `last_error`, `next_retry_at`, `skipped_reason` |
| Заметка (`note`) | `.md` в vault + `notes_fts` (FTS5) | `note_id`, `source_id`, `source_type`, `external_id`, `canonical_url`, `published_at`, `received_at`, `updated_at`, `previous_note_id`, `frontmatter_schema_version`, `title`, `tags`, `topic` (предметная область из профиля) |
| Связь заметок (`note_links`) | SQLite | `source_note_id`, `target_note_id`, `link_type` (`references`/`contradicts`/`updates`/`extends`) |
| Обратная связь (`feedback`) | SQLite | `note_id`, `score`, `comment`, `created_at` |
| История промптов (`prompt_history`) | SQLite | `prompt_name`, `version`, `content`, `is_active`, `created_at`, `approved_by`, `reverted_from` |
| Профиль пользователя (`user_profile`) | `user_profile.yaml` | Цели, задачи, темы, источники, частота сбора, система работы, ядро материалов |

**4 ситуации при обработке нового материала:**
1. **Новый независимый материал** → создать новую заметку.
2. **Повтор уже полученного материала** → пропустить по устойчивому `external_id` и `raw_hash`.
3. **Новая редакция известного материала** → обнаружить изменение источника, предложить обновление связанной заметки (с diff и резервной копией).
4. **Новый материал, противоречащий старому** → создать или обновить заметку с указанием различий, дат и источников, не удаляя прежний контекст автоматически.

### 3.2. Source Layer (Слой источников данных)

**Компоненты:**
- `sources/base.py` — абстрактный `BaseSource` (`fetch()`, `validate()`, `get_metadata()`)
- `sources/telegram.py` — сбор постов `t.me/s/<channel>`
- `sources/youtube.py` — метаданные + субтитры YouTube
- `sources/websites.py` — универсальное извлечение чистого текста со страниц (RSS/Atom + чтение `article`/`main`)
- `sources/papers_docs.py` — локальные PDF/Markdown/TXT, ссылки на arXiv и статьи
- `sources/social_plugins/` — опциональные плагины для Pinterest, VK и др. (не блокируют ядро)
- `sources/registry.py` — реестр источников (`sources.yaml`): добавление, удаление, включение/выключение, валидация, проверка доступности
- `sources/manager.py` — опрос всех активных источников, запись в общую очередь SQLite

**Хранение:** источники — только в `sources.yaml` (Single Source of Truth для конфига). Не дублировать в JSON и SQLite одновременно.

### 3.3. Processing Layer (Слой интеллектуальной обработки)

**Компоненты:**
- `core/interview.py` — `InterviewManager`: вводное интервью (обязательно перед началом формирования БЗ) и периодическое (раз в месяц). Сохраняет профиль в `user_profile.yaml`. cron создаёт только напоминание; интерактивный опрос запускается в CLI.
- `core/relevance.py` — `Relevance Gate`: оценка сырого материала по `user_profile.yaml` (соответствие целям, отсечение рекламы/воды). Пропуск помечается как `skipped` с причиной.
- `core/agent.py` — `KnowledgeAgent`: извлекает элемент из очереди, вызывает один `LLMClient`, получает структурированную заметку, передаёт в KB Writer.
- `processing/llm_client.py` — один универсальный `LLMClient` на базе `httpx` к OpenAI-совместимому API. Для MVP — один проверенный провайдер. Минимальный контракт, интеграционные тесты, фиксация модели, параметров, версии промпта.
- `processing/pipeline.py` — конвейер с надёжностью:
  - состояния очереди: `new`, `processing`, `processed`, `skipped`, `failed`
  - число попыток, текст ошибки, время следующей попытки
  - уникальные ограничения для `external_id` и/или `raw_hash`
  - запись заметки во временный файл с последующим атомарным переименованием
  - транзакции SQLite для связанных изменений
  - блокировка от одновременного запуска двух cron-процессов
  - повторный запуск без создания дублей
  - команда сверки vault и индекса с возможностью восстановления
- `processing/kb_writer.py` — формирует модель заметки (YAML frontmatter, секции, `[[ссылки]]`). `VaultManager` отвечает только за безопасную файловую запись.
- `storage/vault.py` — `VaultManager`: работа с файловой системой Obsidian, создание заметок в тематических папках (по предметам из профиля, а не по источнику). Тип источника (`source_type`) хранится в frontmatter.
- `storage/catalog.py` — `CatalogGenerator`: автоматическая пересборка `Каталог.md`.
- `core/insights.py` — `InsightsEngine`: анализ накопленных заметок. Типы инсайтов с доказательствами:
  - повторяющаяся тема в нескольких независимых источниках;
  - противоречие между двумя заметками;
  - изменение утверждения с течением времени;
  - тема, важная для цели пользователя, но слабо покрытая источниками;
  - связь двух заметок, которая помогает решить конкретную задачу пользователя.
  Каждый инсайт: краткое утверждение, ссылки на заметки-доказательства, тип связи, уровень уверенности, потенциальная польза для профиля.
- `core/update.py` — `KnowledgeUpdater`: сравнение нового материала со старыми заметками через FTS5-поиск; решение — новая заметка / дополнить старую / пропустить дубликат / предложить слияние с diff.
- `core/self_improvement.py` — `SelfImprovementEngine`: сбор метрик, предложение правок промптов и источников, автокорректировка промптов **с явным подтверждением человека** и версионированием для отката. Проверка предлагаемого изменения на тестовом наборе до применения.

**Хранение состояния:** только в SQLite (`state.db`): `raw_queue`, `notes_fts` (FTS5), `note_links`, `feedback`, `prompt_history`, `processed`.

### 3.4. Knowledge Base Layer (Слой базы знаний)

- `storage/vault.py` — `VaultManager`: создание заметок `.md` с YAML frontmatter, папки отражают предметные области и задачи пользователя (из вводного интервью).
- `storage/catalog.py` — `CatalogGenerator`: автогенерация `Каталог.md`.
- `storage/state.py` — `StateManager`: SQLite с таблицами `raw_queue`, `notes_fts`, `note_links`, `feedback`, `prompt_history`, `processed`.

**Взаимодействие:** Processing Layer → запись `.md` в vault → обновление FTS5 и `Каталог.md`.

### 3.5. Agent Integration Layer (Доступ для 6 внешних агентов)

- `agents/mcp_server.py` — `kb-agent mcp-serve`: стандартный протокол Model Context Protocol. Инструменты:
  - `kb_search` — поиск по заметкам (FTS5)
  - `kb_get_note` — получение содержимого заметки
  - `kb_add_source` — добавление источника (с подтверждением человека, не read-only)
  - `kb_record_feedback` — обратная связь по заметке
  - `kb_get_insights` — получение инсайтов
- **Первая версия MCP — read-only:** поиск и чтение заметок. Операции записи/изменения источников — позже с ограничениями и подтверждением.
- `agents/cli_json.py` — флаг `--json` ко всем командам CLI для удобного парсинга внешними агентами (кроме интерактивного интервью в первой версии).
- `prompts/agent_prompt.md` — один универсальный системный промпт (хранится во внешнем файле, редактируемый человеком и SelfImprovementEngine).
- Файлы интеграции в репозитории:
  - `SKILL.md` — навык для Claude Code, Hermes, OpenClaw, Kimi Claw
  - `.cursor/mcp.json` и `.cursorrules` — для Cursor
  - конфигурация для OpenCode
- Вести реестр фактически проверенных интеграций с каждым из шести агентов.

### 3.6. Interface Layer (Взаимодействие с человеком)

- `cli/main.py` — точка входа `kb-agent`
- `cli/commands/ask.py` — `kb-agent ask "<вопрос>"` и `kb-agent search "<запрос>"` (ответ с цитированием, ссылками на заметки и исходные материалы, поведение при недостатке данных — «в базе недостаточно данных»)
- `cli/commands/interview.py` — `interview init`, `interview periodic`, `interview status`
- `cli/commands/sources.py` — `sources add/remove/list/enable/disable` (с валидацией, проверкой доступности, безопасным применением)
- `cli/commands/process.py` — `process` (запуск конвейера вручную)
- `cli/commands/insights.py` — `insights` (показать новые инсайты, зависимости)
- `cli/commands/feedback.py` — `feedback rate <note_id> <score> [comment]`, `feedback tell <message>`
- `cli/commands/self_improve.py` — `self-improve` (показать предложения по улучшению промптов/конфига с подтверждением)
- `cli/ui.py` — интерактивные опросы (Rich Prompt, Confirm, таблицы)

### 3.7. Feedback & Self-Improvement Layer

- `feedback/collector.py` — сбор оценок и комментариев человека по каждой заметке (базовая обратная связь вводится уже на Этапе 2).
- `feedback/metrics.py` — подсчёт метрик: полезность заметок, процент skipped, точность суммаризации.
- `core/self_improvement.py` — рекомендации по промптам, источникам, формату и частоте; предложения в виде diff; проверка на фиксированном наборе до применения; подтверждение пользователя, версионирование и откат.

## 4. Взаимодействие с человеком (сценарии)

### Сценарий 1. Первое знакомство (Вводное интервью)

```
Пользователь запускает: kb-agent interview init

Агент задаёт вопросы (интерактивно, через CLI):
  1. Какова цель базы знаний? (работа, учеба, саморазвитие, хобби)
  2. Какую задачу она должна решать?
  3. Как вы будете использовать БЗ?
  4. Какие источники? (Telegram, YouTube, сайты, исследования, собственные материалы)
  5. Периодичность сбора?
  6. Система работы (по умолчанию Obsidian)?
  7. Есть ли уже ядро материалов?

Результат:
  - user_profile.yaml — профиль с целями, темами, предпочтениями
  - sources.yaml — начальный список источников
  - vault получает "ядро" (если указано)
```
> Интервью обязательно перед началом формирования БЗ. Можно пропустить интерактив и заполнить `user_profile.yaml` вручную через конфиг-файл.

### Сценарий 2. Импорт существующего ядра

```
kb-agent import-core --path /путь/к/материалам --dry-run
kb-agent import-core --path /путь/к/материалам
```
- Dry-run с отчётом о том, что будет импортировано, пропущено, duplicates.
- Сохранение оригиналов без перезаписи.

### Сценарий 3. Фоновая работа (автоматический режим через cron)

```
1. cron запускает сбор из всех активных источников
2. Сырой материал проходит Relevance Gate (отсеивание нерелевантного/рекламы)
3. KnowledgeAgent суммаризирует через один LLMClient
4. Пишет заметку в Obsidian с YAML frontmatter и [[ссылками]] на связанные заметки
5. Обновляет FTS5-индекс и Каталог.md
6. Генерируется Дайджест.md в vault
```

### Сценарий 4. Дайджест (уведомление)

Файл `Дайджест.md` в vault после каждого запуска конвейера:
- сколько элементов получено, обработано, пропущено, завершилось ошибкой;
- какие заметки созданы, обновлены или предложены к объединению;
- ссылки на заметки и исходные материалы;
- наиболее значимые инсайты с указанием заметок-доказательств;
- причины ошибок и пропусков в понятной форме.

### Сценарий 5. Ответ на вопрос человека

```
kb-agent ask "Что я накопил по теме нейросетевого ассистированного программирования?"
kb-agent search "arXiv статьи про трансформеры"

Агент:
  1. Ищет через FTS5 топ релевантных заметок
  2. Читает их содержимое (ограничение контекста по токенам, отбор фрагментов)
  3. Выдаёт синтезированный ответ со ссылками на доказательства
  4. Явно отвечает «в базе недостаточно данных», если информации нет
```

### Сценарий 6. Управление источниками

```
kb-agent sources list
kb-agent sources add telegram ragnarokzone
kb-agent sources add website https://example.com
kb-agent sources add papers arxiv:2305.12345
kb-agent sources add personal /home/user/notes/*.md
kb-agent sources remove telegram paragonzone
kb-agent sources enable youtube
```
Валидация, проверка доступности источника, безопасное применение изменений.

### Сценарий 7. Периодическое интервью (раз в месяц)

```
cron создаёт напоминание: «Время пройти ежемесячное интервью»
Пользователь запускает: kb-agent interview periodic

Агент спрашивает:
  - Изменились ли цели и задачи?
  - Добавить/удалить источники?
  - Удовлетворены ли качеством заметок?
  - Какие инсайты были полезны?

Результат: обновление user_profile.yaml, корректировка источников и промптов
```

### Сценарий 8. Обратная связь и саморазвитие

```

kb-agent feedback tell "Нужно больше акцента на практические инструменты"
```

## 5. Потоки данных между компонентами

### Поток А: Сбор и интеллектуальная обработка

```
Источник (Telegram/YouTube/Сайт/arXiv/Личный файл)
    ↓ fetch
Source Layer → Очередь raw_queue (SQLite, состояние new)
    ↓ Relevance Gate (по user_profile.yaml)
Processing Layer (KnowledgeAgent + один LLMClient)
    ↓ структурированная заметка
Knowledge Base Layer (kb_writer → VaultManager)
    ↓ атомарная запись .md с [[ссылками]] + YAML frontmatter
Obsidian Vault / Каталог.md
    ↓ FTS5-индексация + note_links (граф связей) в транзакции SQLite
    ↓ Дайджест.md в vault
Пользователь: вопрос → FTS5 поиск → ответ со ссылками
```

### Поток Б: Интервью, обратная связь, саморазвитие

```
CLI / MCP
    ↓ ответы / оценки
InterviewManager / FeedbackCollector
    ↓ сохранить
SQLite: feedback, prompt_history + YAML: user_profile.yaml, sources.yaml, промпты
    ↓ использовать
SelfImprovementEngine → предложение правок в виде diff (требует подтверждения человека, проверка на тестовом наборе, откат)
    ↓ следующее запуск конвейера
Processing Layer использует обновлённые промпты и фильтры
```

## 6. План реализации по этапам (логичный порядок)

### Этап 0. Уточнение scope и инвентаризация (1–2 дня)

**Состав:** локальный однопользовательский режим, источники MVP (1–2), один LLM-провайдер, судьба существующих скриптов, схема данных, набор материалов и вопросов для проверки качества, проверка LICENSE.

**Критерии готовности:**documented решения по скриптам, источники MVP выбраны, схема данных утверждена.

---

### Этап 1. Основа, онбординг и импорт ядра (3–4 дня)

**Состав:**
- `pyproject.toml` с минимальными зависимостями (pydantic, typer, rich, httpx, pytest, ruff)
- Пакет `kb_agent/` со структурой модулей
- `config.py` на Pydantic Settings (`.env`, `config.yaml`)
- `storage/state.py` — SQLite с таблицами: `raw_queue`, `notes_fts` (FTS5), `note_links`, `feedback`, `prompt_history`, `processed`
- Миграции SQLite вместо разового создания всех таблиц
- `core/interview.py` — `InterviewManager`, команда `kb-agent interview init`, создание `user_profile.yaml`
- Импорт существующих материалов с `dry-run` и отчётом, сохранение оригиналов
- Логирование без утечки чувствительного содержимого
- Проверка и/o создание файла `LICENSE` (MIT)

**Критерии готовности:**
- `pip install -e .` работает
- `kb-agent --version` выводит версию
- `kb-agent interview init` создаёт `user_profile.yaml`
- SQLite с FTS5 создаётся при первом запуске

---

### Этап 2. Надёжный вертикальный срез наполнения (1–1,5 недели)

**Цель:** повторный запуск на тех же данных не создаёт дублей; после искусственного сбоя систему можно безопасно продолжить.

**Задачи:**
1. `sources/base.py`, `telegram.py`, `youtube.py` (1–2 приоритетных источника)
2. `sources/registry.py` (`sources.yaml`), `sources/manager.py`
3. `core/relevance.py` — Relevance Gate
4. `processing/llm_client.py` — один `LLMClient` (один проверенный провайдер)
5. `core/agent.py` — `KnowledgeAgent`
6. `processing/pipeline.py` — конвейер с Relevance Gate, состояниями очереди, атомарной записью, транзакциями, блокировкой от параллельных запусков
7. `processing/kb_writer.py` + `storage/vault.py` — запись `.md` в тематических папках, YAML frontmatter, `[[ссылки]]`
8. `storage/catalog.py` — автогенерация `Каталог.md`
9. `storage/state.py` — FTS5-индексация, граф `note_links`
10. Дайджест запуска (`Дайджест.md` в vault)
11. Базовая обратная связь (`feedback rate/tell`)
12. Базовое расписание сбора через cron (ручной запуск + cron)
13. CLI: `kb-agent sources add/remove/list`, `kb-agent process`

**Критерии готовности:**
- `kb-agent process` собирает, фильтрует, суммаризирует и пишет заметки в vault
- Повторный запуск на тех же данных не создаёт дублей
- После сбоя система восстанавливается без расхождения vault и SQLite
- Заметки содержат frontmatter, `[[ссылки]]`, тип источника, метаданные происхождения
- FTS5-индекс обновляется после каждой заметки
- `Каталог.md` пересобирается автоматически
- Дайджест создаётся после каждого запуска

---

### Этап 3. Поиск, ответы и управляемая актуализация (1 неделя)

**Задачи:**
1. `cli/commands/ask.py` — `kb-agent ask "<вопрос>"`, `kb-agent search "<запрос>"` (FTS5 → контекст → LLM-ответ со ссылками)
2. Проверка качества русскоязычного поиска на проверочном наборе (словоформы, синонимы, транслитерация, контекстный бюджет, поведение при недостатке данных)
3. `core/update.py` — `KnowledgeUpdater` (сравнение через FTS5, 4 ситуации актуализации, предложение слияния с diff и резервной копией)
4. `core/insights.py` — `InsightsEngine` (первые ограниченные инсайты: повторяющиеся темы, противоречия, пробелы в покрытии)
5. CLI: `kb-agent ask`, `kb-agent search`, `kb-agent insights`, `kb-agent update check`

**Критерии готовности:**
- `kb-agent ask` возвращает ответ со ссылками на заметки или явное «в базе недостаточно данных»
- `KnowledgeUpdater` находит дубликаты и предлагает слияние/обновление
- `InsightsEngine` показывает неочевидные связи с доказательствами

---

### Этап 4. Доступ для внешних агентов (MCP + Skills + CLI JSON) (3–5 дней)

**Цель:** выполнение требования о доступности для Hermes, Cursor, ClaudeCode, OpenCode, OpenClaw, Kimi Claw.

**Задачи:**
1. `agents/mcp_server.py` — MCP-сервер (read-only сначала: `kb_search`, `kb_get_note`, `kb_get_insights`)
2. Команда `kb-agent mcp-serve`
3. Флаг `--json` ко всем CLI-командам (кроме интерактивного интервью в первой версии)
4. `prompts/agent_prompt.md` — один универсальный системный промпт
5. Готовые манифесты: `SKILL.md`, `.cursor/mcp.json`, `.cursorrules`, конфиг OpenCode
6. Проверка интеграции с каждым из шести агентов, ведение реестра проверенных интеграций
7. Операции записи/изменения источников — позже с подтверждением человека

**Критерии готовности:**
- Внешние агенты могут искать и читать заметки через MCP
- CLI возвращает JSON при `--json`
- Все 6 целевых агентов имеют готовые инструкции интеграции
- Ведётся реестр фактически проверенных интеграций

---

### Этап 5. Развитие под наблюдением человека (4–5 дней)

**Задачи:**
1. `feedback/collector.py`, `feedback/metrics.py`
2. `core/self_improvement.py` — предложения по промптам/источникам в виде diff, автокорректировка с подтверждением человека, версионирование промптов для отката, проверка на тестовом наборе до применения
3. Напоминания о ежемесячном интервью (cron создаёт напоминание, интерактивный запуск в CLI)
4. CLI: `kb-agent feedback rate/tell`, `kb-agent interview periodic`, `kb-agent self-improve`
5. Дополнительные источники и гибридный поиск только по доказанной потребности

**Критерии готовности:**
- Человек оценивает заметки и оставляет комментарии
- `kb-agent self-improve` показывает предложения с подтверждением

## 8. Риски и способы их митигации

| Риск | Вероятность | Влияние | Митигация |
|------|-------------|---------|-----------|
| Ломка HTML-структуры Telegram (`t.me/s/`) | Средняя | Высокое | Абстракция `BaseSource`, можно перейти на Telethon API |
| YouTube блокирует yt-dlp | Средняя | Среднее | Кэширование, паузы, резерв RSS-каналы |
| LLM возвращает неструктурированный ответ | Средняя | Высокое | Строгий системный промпт, валидация Pydantic, повторные попытки |
| Соцсети с защитой (Pinterest, VK) | Высокая | Среднее | Вынесены в опциональные плагины, не блокируют ядро |
| Потеря данных при актуализации | Низкая | Высокое | Резервное копирование перед перезаписью, режим "только предложение" |
| Автокорректировка промптов ухудшает качество | Средняя | Среднее | Только с подтверждением человека, хранение предыдущей версии для отката, проверка на тестовом наборе |
| Рассинхрон конфига (YAML vs SQLite) | Низкая | Среднее | Жёсткое разделение: конфиг — только YAML/MD, состояние — только SQLite |
| Промпт-инъекции из обработанного текста | Средняя | Высокое | Изоляция исходного текста от системных инструкций, явные правила приватности, MCP read-only сначала |

## 9. Безопасность и приватность (сквозное требование)

До разработки определить:
- какие данные разрешено отправлять облачной модели;
- какие каталоги и типы файлов исключены из сбора;
- как скрываются секреты и чувствительные данные в логах;
- как исходный текст изолируется от системных инструкций;
- почему обработка источника не даёт ему права запускать инструменты или менять конфигурацию;
- какие MCP-операции доступны только для чтения, а какие требуют подтверждения;
- как ограничиваются доступ внешних агентов к файловой системе и изменениям источников.

## 11. Критерии приёмки MVP

MVP можно считать соответствующим пожеланиям, если пользователь может выполнить следующий сквозной сценарий:

1. Пройти вводное интервью и получить валидный профиль с целями, темами, источниками и частотой.
2. Импортировать существующее ядро материалов, предварительно увидев dry-run и не потеряв оригиналы.
3. Подключить приоритетный источник, изменить его настройки и отключить без ручного редактирования внутренней БД.
4. Запустить наполнение вручную и по настроенному расписанию.
5. Получить структурированные заметки в Obsidian с тематикой, ссылками, датами и происхождением.
6. Повторно обработать те же данные без дублей.
7. Получить дайджест о созданных, обновлённых, пропущенных и ошибочных элементах.
8. Изменить исходный материал в тестовом источнике и получить предложение обновить связанную заметку, а не молчаливую перезапись.
9. Задать вопрос и получить ответ со ссылками на доказательства либо явное сообщение о недостатке данных.
10. Оценить заметку/ответ и оставить произвольный комментарий.
11. Восстановить индекс и состояние после тестового сбоя без расхождения между vault и SQLite.
12. Убедиться, что вредоносные инструкции внутри обрабатываемого текста не меняют конфигурацию и не вызывают посторонние действия.

Для полного релиза дополнительно нужны ежемесячное интервью, ограниченное самоулучшение с откатом и подтверждённые сценарии доступа для целевых внешних агентов.
