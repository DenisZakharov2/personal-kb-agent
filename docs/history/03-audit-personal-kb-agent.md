# Аудит репозитория personal-kb-agent

**Репозиторий:** <https://github.com/DenisZakharov2/personal-kb-agent>  
**Проверенная версия:** `ade9f03aa21fc7987e8e3b290ded1686b176b4a4`  
**Дата аудита:** 2026-11-04  
**Область:** пакет `kb_agent`, CLI, MCP-сервер, сборщики Telegram/YouTube, SQLite и FTS5, файлы vault, pending-операции, упаковка, GitHub Actions, документация и история секретов.

## 1. Краткое заключение

Проект выглядит как продуманный прототип: есть разделение на источники, обработку, хранение и интерфейсы; параметризованные SQL-запросы; безопасная сериализация frontmatter; ограничение поисковой выдачи; таймауты и повторные запросы к LLM; локальный MCP-транспорт stdio.

Однако текущую версию нельзя считать надёжным автоматическим помощником базы знаний. Основная проблема не в отдельных опечатках, а в расхождении заявленных гарантий с фактическим поведением:

- MCP-операции с источниками подтверждаются как `applied`, но не меняют файл, который реально читает сборщик.
- Подтверждение человека не является границей безопасности: сам AI-агент может вызвать `kb_confirm_change`.
- YouTube-сборщик содержит воспроизводимый `NameError`, игнорирует `limit` и повторно скачивает субтитры для уже поставленных в очередь видео.
- Импорт существующих материалов с `--apply` ничего не импортирует, хотя сообщает об успехе.
- После части сбоев заметка остаётся в vault, не попадает в поиск и не повторяется автоматически.
- Scheduled GitHub Actions запускает старый JSONL-конвейер, а не приложение `kb-agent`; секреты записываются в `.env`, который эти скрипты не читают.
- MCP-сервер объявляет пустой набор capabilities, хотя спецификация требует объявлять поддержку tools.
- Wheel не содержит файлы промптов и примеры конфигурации, а `yt-dlp` не объявлен зависимостью.
- «Самоулучшение» пока представлено метриками и заглушками, а не замкнутым, проверяемым циклом.

**Общая оценка:** хорошая основа для MVP, но перед ежедневной автоматической работой нужно исправить целостность данных, MCP-контракты, восстановление после сбоев и тестовый контур. Удалённых критических уязвимостей вроде очевидного SQL injection или RCE в основном пакете не обнаружено; главные риски относятся к целостности конфигурации, потере/рассинхронизации данных, приватности и indirect prompt injection.

## 2. Методика и ограничения

### Что проверено

- Статическое чтение всех основных модулей `kb_agent` и ключевых legacy-скриптов.
- `python3 -m compileall -q kb_agent scripts` — синтаксических ошибок не найдено.
- `pytest -q` — тестов в репозитории нет (`no tests ran`).
- Сборка wheel через `pip wheel . --no-deps --no-build-isolation`; проверен состав архива.
- Локальные рантайм-проверки с временными SQLite/vault и заглушками внешних вызовов.
- Проверка MCP-сервера по коду и официальной спецификации MCP.
- Поиск секретоподобных строк в текущем дереве и в пяти доступных коммитах истории.
- Сверка README, SKILL.md, docs и фактических путей вызовов.

### Ограничения

- Внешние Telegram, YouTube и LLM API не вызывались; сетевые сценарии проверялись на заглушках.
- Пакет `mcp` в среде аудита отсутствовал, а доступ к PyPI был недоступен, поэтому полный MCP handshake с реальным SDK не запускался. Проблема capabilities установлена по коду и нормативному тексту спецификации.
- `ruff`, `mypy`, `bandit` и `pip-audit` не запускались. Точного аудита CVE зависимостей сделать нельзя ещё и потому, что в репозитории нет lock-файла.
- Исходный код репозитория не изменялся.

В отчёте метка **«воспроизведено»** означает локальный запуск; **«по коду»** — вывод из путей вызовов без внешнего интеграционного прогона.

## 3. Что уже сделано хорошо

- SQL-параметры передаются через placeholders; пользовательский FTS-запрос очищается от операторов FTS5.
- `VaultManager` использует `yaml.safe_dump`, slug для имён файлов и запись через временный файл.
- YAML из профиля читается через `safe_load`.
- Подпроцессы `yt-dlp` запускаются списком аргументов, без `shell=True`.
- Есть сетевые таймауты, retry/backoff для LLM и ограничение `limit` в поиске.
- CLI и MCP используют общие компоненты поиска и хранения, а не полностью отдельные реализации.
- Pending-подтверждение — правильная продуктовая идея; проблема в его текущей границе доверия и исполнении.
- В текущем дереве секретоподобных значений не найдено; `.env` и основные локальные данные включены в `.gitignore`.

## 4. Высокий приоритет P1

### P1-01. MCP меняет таблицу `sources`, а сборщик читает `sources.yaml`

**Где:**  
`kb_agent/storage/pending.py:169–182`; `kb_agent/storage/state.py:481–536`; `kb_agent/sources/manager.py:40–49, 88–106`; `kb_agent/sources/registry.py:23–75`.

**Проблема:** существуют два несинхронизированных «источника истины». Pending-операции пишут в SQLite-таблицу `sources`, но `SourceManager` получает источники только из `SourceRegistry`, то есть из YAML.

**Воспроизведено:** после успешного pending `add_source` в SQLite появилась одна запись, а YAML-реестр остался пустым; при этом pending получил статус `applied`.

**Влияние:** агенту возвращается ложное подтверждение. Добавленный канал не собирается, удалённый продолжает собираться, выключение источника не действует.

**Решение:** выбрать одну каноническую модель:

1. Предпочтительно для приложения: SQLite — каноническое хранилище источников; CLI и MCP используют один `SourceService`; YAML — только явный import/export.
2. Альтернатива: оставить YAML каноническим и перевести `PendingManager` на `SourceRegistry`, удалив таблицу `sources`.

Не следует пытаться поддерживать две независимые записи без транзакции и механизма разрешения конфликтов.

### P1-02. AI-агент может сам подтвердить своё изменение

**Где:** `kb_agent/agents/mcp_server.py:170–183, 368–391`; `kb_agent/storage/pending.py:102–143`.

**Проблема:** `kb_confirm_change` доступен через тот же model-controlled MCP-интерфейс и жёстко передаёт `confirmed_by="user"`. Отдельной аутентификации человека, интерактивного вопроса или проверки происхождения вызова нет.

**Влияние:** цепочка `kb_remove_source → kb_confirm_change` может быть выполнена агентом без участия владельца. Это особенно важно при indirect prompt injection из заметки или собранного текста. MCP-хост может сам показывать диалог подтверждения, но приложение не вправе считать это своей гарантией.

**Решение:**

- Убрать `kb_confirm_change` из инструментов, доступных модели.
- Оставить подтверждение только в отдельном человеческом канале: интерактивный CLI или локальный UI.
- Pending должен содержать diff, `payload_hash`, `base_revision`, автора, время истечения и одноразовый идентификатор.
- При подтверждении атомарно проверить `status='pending'`, hash и актуальную ревизию объекта.
- Добавить `reject`, срок действия и понятный audit trail.

### P1-03. YouTube: `NameError` в штатной обработке ошибок субтитров

**Где:** `kb_agent/sources/youtube.py:98–141`, особенно строки 110, 113, 123, 132, 137, 140.

**Проблема:** `_fetch_transcript(video_id, ...)` использует переменную `vid`, которая в этой функции не определена.

**Воспроизведено:** при смоделированном ненулевом коде возврата `yt-dlp` получено `NameError: name 'vid' is not defined`.

**Влияние:** ошибка самого `yt-dlp` превращается в ошибку Python; вместо перехода к следующему языку или видео срабатывает внешний обработчик источника. Это делает YouTube-сбор непредсказуемым именно на негативных сценариях.

**Решение:** заменить `vid` на `video_id`, добавить тесты на timeout, ненулевой return code, отсутствие файла, битый JSON и пустые субтитры.

### P1-04. YouTube игнорирует `limit` и повторно выполняет дорогие запросы

**Где:** `kb_agent/sources/youtube.py:176–228`; `kb_agent/storage/state.py:469–477`.

**Проблемы:**

- Параметр `limit` передаётся в коллектор, но цикл `for v in videos` его не использует.
- Таблица `processed` проверяется через `is_processed`, но `mark_processed_key` нигде не вызывается.
- Проверка `enqueue` на дубликат происходит только после скачивания субтитров. Поэтому при следующем запуске старое видео снова обращается к `yt-dlp`, и лишь затем отбрасывается.
- Метаданные канала запрашиваются целиком, без ограничения выдачи на раннем этапе.

**Воспроизведено:** при трёх входных видео и `limit=1` в очередь попали все три.

**Влияние:** не выполняется настройка пользователя; растут время, трафик и риск блокировки; scheduled запуск становится всё медленнее по мере роста канала.

**Решение:** проверять существование `(source_id, external_id)` до скачивания субтитров; ограничивать список до цикла; рассмотреть `--flat-playlist` и раннее ограничение выборки; удалить мёртвую таблицу `processed` либо действительно использовать её.

### P1-05. `interview import-core --apply` — фиктивный импорт

**Где:** `kb_agent/core/import_core.py:39–64`; `kb_agent/cli/commands/interview.py:89–123`.

**Проблема:** `import_files` лишь добавляет строку «Импортировано» в отчёт. Нет чтения содержимого, копирования в vault, записи в очередь или FTS-индексации.

**Воспроизведено:** для одного Markdown-файла отчёт показал `imported=1`, `errors=0`, но поиск остался пустым.

**Дополнительно:** CLI всегда печатает «Будут импортированы», даже при `--apply`.

**Влияние:** пользователь может считать материалы перенесёнными и потерять к ним доступ после удаления оригиналов.

**Решение:** до релиза либо скрыть `--apply`, либо реализовать идемпотентный импорт: hash пути/содержимого, dry-run diff, обработка frontmatter, запись в vault, индексация, отчёт о фактических действиях и повторный запуск без дублей.

### P1-06. Нет восстановления очереди и согласованности vault ↔ FTS

**Где:** `kb_agent/processing/pipeline.py:107–209`; `kb_agent/storage/state.py:282–321`.

**Проблемы:**

- Выбираются только элементы `new`. `failed` никогда не повторяются, несмотря на поля `attempts`, `last_error`, `next_retry_at`.
- Если процесс упал после `mark_processing`, элемент навсегда остаётся `processing`.
- Запись файла, индексация и `mark_processed` — отдельные операции без протокола восстановления.
- `get_next_new` и `mark_processing` не образуют атомарный захват задания.

**Воспроизведено:** при исключении в `index_note` файл заметки остался в vault, запись стала `failed`, а `get_next_new()` вернул `None`. Получилась заметка, которой нет в поиске и которую конвейер сам не исправит.

**Влияние:** потеря видимости знаний, дубли при параллельных запусках, накопление «зависших» заданий.

**Решение:** идемпотентный workflow с lease:

- атомарный захват задания в `BEGIN IMMEDIATE`;
- `processing_started_at`, `lease_expires_at`, `attempts`, backoff;
- детерминированный `note_id` на основе ключа задания или сохранённый в БД до записи;
- отдельные повторяемые шаги `summarize → write → index → done`;
- команда `kb-agent process retry` и reconciler, который находит файл и восстанавливает индекс;
- один scheduler/worker либо корректная конкурентная обработка с WAL и busy timeout.

Одна SQLite-транзакция не сделает файловую систему и БД атомарными вместе — нужна именно идемпотентность и сверка состояния.

### P1-07. Scheduled CI не наполняет базу знаний

**Где:** `.github/workflows/collect.yml:19–49`; `scripts/collect_telegram.py`; `scripts/collect_youtube.py`; `scripts/legacy/README.md:31–47`.

**Проблемы:**

- Workflow устанавливает только зависимости legacy-скриптов, но не сам пакет и LLM-конфигурацию.
- Запускаются JSONL-сборщики, а не `kb-agent process run`.
- `KB_*` из GitHub Secrets записываются в `.env`; legacy-скрипты читают только `os.getenv`, поэтому значения не попадают в процесс.
- Артефакт `_queue.jsonl` не имеет потребителя в основном приложении.
- `processed.txt` Telegram не входит в список сохраняемых артефактов.
- Vault и `state.db` не сохраняются; суммаризация и индексация не выполняются.

Это ограничение частично признано в `scripts/legacy/README.md`, но остаётся неисправленным.

**Влияние:** зелёный scheduled workflow создаёт видимость автоматического наполнения KB, хотя основная база не меняется; сбор идёт с default-каналами.

**Решение:** до исправления отключить schedule или явно назвать workflow `Legacy queue collector`. Затем перевести его на установленный пакет, `$GITHUB_ENV`, реальный `kb-agent process run`, сохранение состояния и явные ненулевые exit codes при ошибках. Секреты и персональную базу нельзя случайно включать в артефакты.

### P1-08. MCP-сервер не объявляет capability `tools`

**Где:** `kb_agent/agents/mcp_server.py:400–411`.

**Проблема:** передаётся `capabilities={}`. По спецификации MCP сервер, поддерживающий tools, обязан объявить capability `tools`.

**Влияние:** отдельные клиенты могут продолжить работать, но строгий клиент вправе считать инструменты неподдерживаемыми. Это создаёт несовместимость, которую трудно диагностировать.

**Решение:** формировать capabilities через `app.get_capabilities(notification_options=NotificationOptions(), experimental_capabilities={})`, как в официальном low-level примере, и добавить настоящий integration test `initialize → tools/list → tools/call`.

### P1-09. Установленный пакет теряет runtime-ресурсы; YouTube-зависимость не установлена

**Где:** `pyproject.toml:34–59`; `kb_agent/config.py:15–25`; `kb_agent/core/prompts.py:23–35`; `kb_agent/sources/registry.py:198–204`.

**Воспроизведено:** собранный wheel содержит 50 файлов пакета, но не содержит `config/prompts/agent_prompt.md`, `config/sources.example.yaml` и `config/user_profile.example.yaml`.

**Проблемы:**

- `package-data` применяется к пакетам `kb_agent*`, а нужные ресурсы лежат на верхнем уровне репозитория.
- При обычной установке `PROJECT_ROOT` указывает в область `site-packages`, а не в рабочий проект пользователя. Оттуда пытаются читаться `.env` и `config/*`; туда же по умолчанию направляются `data/*`, что может закончиться ошибкой прав доступа.
- `yt-dlp` вызывается как обязательный внешний бинарь для YouTube, но отсутствует в зависимостях и инструкции установки.

**Влияние:** quickstart работает только в editable-клоне и только при дополнительной ручной установке `yt-dlp`; обычная установка wheel ведёт к пустым источникам и отсутствующему seed-промпту.

**Решение:** перенести packaged resources внутрь `kb_agent/resources` и читать через `importlib.resources`; пользовательские данные размещать через `platformdirs`/XDG или явный `KB_DATA_DIR`; добавить extra `youtube = ["yt-dlp>=..."]` и проверку наличия бинаря с понятной ошибкой; тестировать установку wheel в чистом окружении.

### P1-10. «Самоулучшение» и управление промптами не образуют рабочий цикл

**Где:** `kb_agent/core/self_improvement.py:140–143, 147–187, 264–274`; `kb_agent/cli/commands/self_improve.py:56–81`; `kb_agent/processing/llm_client.py:174–214`; `kb_agent/core/search.py:87–108`.

**Проблемы:**

- `list_proposals()` всегда возвращает `[]`.
- `_run_test_suite()` всегда возвращает `True`.
- CLI прямо сообщает, что автоматических предложений нет; propose/apply не подключены.
- `confirmed_by` — просто строка, а не доказательство подтверждения.
- Активный `agent_prompt` применяется к ответам на вопросы, но суммаризация использует отдельный жёстко зашитый промпт.
- `apply_prompt_proposal` сохраняет новую активную запись, не снимая `is_active` со старой в одной транзакции.

**Влияние:** заявленный этап 5 не обеспечивает проверяемых улучшений; откат промпта меняет только часть поведения; оценки не влияют на качество конвейера.

**Решение:** разделить `summarize_prompt` и `answer_prompt`, хранить proposals в SQLite, связывать их с eval-набором и отчётом тестов, применять версии атомарно, а до реализации убрать статус «✅ самоулучшение» из README.

## 6. Безопасность и приватность

### 6.1. Основной риск — цепочка недоверенного контента и действий агента

Сейчас возможна такая логическая цепочка:

1. Пост или транскрипт содержит инструкцию для AI.
2. LLM превращает его в заметку; фильтрации инструкций как данных нет.
3. Внешний агент получает текст через `kb_get_note`.
4. Тот же агент имеет write-инструменты и может вызвать подтверждение сам.

Разделение system/user в `LLMClient` полезно, но не «изолирует» текст в смысле гарантированной защиты от prompt injection. Нужна защита на уровне полномочий, а не только формулировок промпта.

Минимальный набор:

- read-only MCP по умолчанию и отдельный opt-in для proposals;
- никакого confirm в model-controlled интерфейсе;
- явное происхождение каждого фрагмента: URL, source, note_id, `untrusted_content`;
- никаких автоматических действий на основании текста заметки;
- allowlist источников и URL, особенно потому что `yt-dlp` поддерживает больше протоколов и сайтов, чем один YouTube;
- ограничение сетевых исходящих запросов там, где это уместно;
- тесты на malicious note, пытающуюся удалить источник или изменить профиль.

### 6.2. Заявление «все данные остаются локально» неверно

**Где:** `README.md:226–230`; `kb_agent/processing/llm_client.py:96–112, 174–214`.

Сырые тексты и найденные заметки отправляются настроенному внешнему OpenAI-compatible endpoint. Для Ollama это может быть локальный контур, но для OpenAI/Kimi/OpenRouter — внешняя передача данных.

Нужно документировать, какие поля отправляются, кому и когда; добавить режим локальной обработки, исключения для приватных источников/заметок, redaction и настройку retention на стороне провайдера, если она доступна. В MCP стоит поддержать метки чувствительности и запрет выдачи отдельных заметок внешнему агенту.

### 6.3. Опасный latent API записи конфигурации

`SelfImprovementEngine.apply_config_proposal` (`core/self_improvement.py:189–213`) принимает `proposal.target_name` как произвольный путь и перезаписывает его. Сейчас метод не подключён к CLI/MCP, поэтому это не удалённая уязвимость текущей версии. Перед подключением агента необходимо ограничить путь строгим allowlist конкретных конфигурационных файлов и добавить атомарную запись и проверку diff.

### 6.4. Что не выглядит уязвимым в проверенном коде

- Не найдено очевидной SQL-инъекции в основных операциях.
- Имена тем/заголовков проходят slug, поэтому прямого path traversal через них не видно.
- YAML не загружается небезопасным объектным loader.
- `yt-dlp` вызывается без shell interpolation.
- MCP использует stdio, а не открытый сетевой порт.

Это не заменяет полноценный security test, но сужает основные риски до доверия агенту, целостности операций, внешних источников и приватности.

## 9. Чего не хватает функционально

### Для надёжной базы знаний

- Настоящий импорт Markdown/TXT и повторная индексация существующего vault.
- Восстановление failed/processing, ручной retry и просмотр skipped с возможностью вернуть материал.
- Единый notes catalogue с provenance и rebuildable search index.
- Команды `doctor`, `reindex`, `retry`, `backup/export`.
- Идемпотентное обновление заметки при изменении источника, удаление/архивация и настоящее слияние дублей.
- Сохранение raw content отдельно от суммаризации, чтобы можно было переименовать модель/промпт и пересобрать заметку.
- Метаданные модели, версии промпта, usage/latency/cost для каждой генерации.
- Управление приватностью и исключение чувствительных материалов из внешних LLM/MCP.
- RSS/сайты/локальные файлы заявлены продуктовой мотивацией, но рабочие источники пока только Telegram и YouTube.

### Для качества AI

- Structured output и валидация ответов LLM.
- Оценка релевантности, не зависящая от количества тем в профиле.
- Chunking длинных транскриптов, поиск по фрагментам и цитаты с offsets.
- Нормальный ranking и фильтры по source/topic/date/tags.
- Отдельный eval-набор: вопрос, ожидаемые note_id/URL, критерии полноты и запрещённые выдумки.
- Метрики retrieval и generation отдельно: hit rate, citation correctness, insufficient-data accuracy, feedback по конкретному ответу.
- Версии промптов для разных задач и атомарная активация после проверки.

Векторный поиск не является первым необходимым шагом. Сначала стоит исправить метаданные, chunking, BM25, цитирование и evals. Гибрид FTS + embeddings имеет смысл добавлять после появления измеримых случаев, где lexical search действительно проигрывает.

## 10. Рекомендуемая архитектура связки с AI-агентом

### 10.1. Роль kb-agent

Не нужно превращать MCP-сервер во второго автономного агента поверх внешнего агента. Полезнее сделать его надёжным локальным слоем:

- retrieval с проверяемыми источниками;
- хранение и индексация;
- подготовка изменений;
- исполнение только подтверждённых человеком операций;
- аудит и восстановление.

`kb-agent ask` можно оставить для человека, но внешнему AI-агенту обычно лучше возвращать evidence, а не прогонять второй LLM-ответ внутри `kb_search`.

### 10.2. Единые application services

CLI и MCP должны вызывать одни и те же сервисы:

- `SourceService`: нормализация, валидация, list/add/remove/enable;
- `IngestService`: collect, claim, retry, summarize, reconcile;
- `NoteService`: import, write, reindex, provenance;
- `SearchService`: retrieval, snippets, filters, pagination;
- `ChangeService`: propose, inspect, confirm out-of-band, reject, audit;
- `PromptService`: versions, evals, atomic activation.

Сейчас расхождение CLI/MCP и YAML/SQLite возникло именно из-за обхода единого сервисного слоя.

### 10.3. Источники истины

Рекомендуемая модель:

- Markdown в vault — канонический контент заметок, доступный человеку.
- SQLite `notes` — метаданные и состояние синхронизации с путём/hash файла.
- FTS/embeddings — rebuildable projections, а не единственная копия metadata.
- SQLite `sources` — каноническая конфигурация для программы; YAML только import/export. Если важнее ручное редактирование YAML, тогда наоборот: YAML единственный canonical store, а таблицу удалить.
- Pending и prompt history — SQLite с revisions и audit fields.

### 10.4. MCP-контракт

Для чтения:

- `kb_search`: query, filters, limit, cursor → structured items с `note_id`, `title`, `snippet`, `url`, `topic`, `tags`, `rank`, `content_hash`.
- `kb_get_note`: note_id, optional max_bytes/chunk → content плюс provenance и truncation flag.
- `kb_get_insights`: только реально вычисленные типы инсайтов с confidence/evidence.
- `kb_list_changes`, `kb_get_change`: чтение предложений и diff.
- `kb_health`: состояние БД, очереди, индексации и последних ошибок.

Для записи:

- `kb_propose_source_change`;
- `kb_propose_profile_change`;
- `kb_propose_note_change` с unified diff;
- никакого `kb_confirm_change` у модели.

Подтверждение человеком: `kb-agent changes show <id>` и `kb-agent changes confirm <id>`. Payload и base revision должны быть связаны с одноразовым подтверждением; после истечения TTL предложение требует пересоздания.

### 10.5. Машинный вывод вместо Markdown-парсинга

Пример результата поиска:

```json
{
  "items": [
    {
      "note_id": "2026-11-04T10_ab12cd34",
      "title": "Пример заметки",
      "snippet": "Релевантный фрагмент…",
      "source_url": "https://example.com/source",
      "topic": "ИИ",
      "tags": ["mcp", "rag"],
      "rank": -2.31,
      "content_hash": "sha256:…"
    }
  ],
  "next_cursor": null,
  "truncated": false
}
```

Markdown можно оставить как дополнительный backward-compatible text block, но агент не должен извлекать ID и статусы из человекочитаемых строк.

### 10.6. Контроль качества изменений

Перед активацией нового промпта:

1. Сформировать diff и причину.
2. Запустить фиксированный eval-набор с той же моделью и retrieval-настройками.
3. Сохранить метрики, ошибки и стоимость.
4. Показать человеку diff и результат сравнения.
5. После внешнего подтверждения атомарно активировать новую версию.
6. Хранить возможность отката ко всей конфигурации, а не только к тексту промпта.

## 11. Приоритизированный план работ

### Волна 0 — перестать сообщать ложный успех

1. Исправить `vid → video_id`, применить `limit` и раннюю дедупликацию YouTube.
2. Убрать `kb_confirm_change` из MCP.
3. Унифицировать хранение источников; проверять результат каждой pending-операции.
4. Исправить MCP capabilities.
5. Скрыть неработающий `--apply` либо реализовать импорт.
6. Отключить/переименовать legacy schedule до перевода на основной конвейер.
7. Синхронизировать README/SKILL/docs и снять «✅» с заглушек.

### Волна 1 — целостность и восстановление

1. Идемпотентная очередь с lease, retry и reconciler.
2. Каноническая `notes`, provenance и `reindex`.
3. Атомарные pending transitions и optimistic revisions.
4. Безопасные пользовательские пути, packaged resources, `yt-dlp` extra.
5. Явные ошибки CLI и digest по каждому источнику.

### Волна 2 — тестовый и release-контур

1. Unit/integration/regression tests из раздела 12.
2. GitHub Actions: lint, typecheck, tests, wheel build/install, MCP protocol smoke test.
3. Lock для CI, dependency updates и audit; минимальные permissions Actions.
4. `doctor`, rotating logs, run_id/change_id и наблюдаемость ошибок.

### Волна 3 — качество работы с AI-агентом

1. Structured MCP input/output, пагинация, лимиты и annotations.
2. Out-of-band human confirmation с diff/hash/revision/TTL.
3. Structured LLM output и prompt registry по задачам.
4. Search snippets, chunking, filters и цитаты.
5. Evals и сохраняемые improvement proposals; только затем включать «самоулучшение».

## 12. Минимальный набор тестов и Definition of Done

### Обязательные regression-тесты

- YouTube: timeout/nonzero exit не вызывает `NameError`; `limit=1` обрабатывает одно видео.
- Повторный сбор не скачивает субтитры для уже существующего `(source_id, external_id)`.
- MCP/CLI add/remove/enable меняют один и тот же видимый реестр источников.
- Удаление несуществующего источника возвращает ошибку, а не `applied`.
- Модель не имеет confirm-инструмента; человек подтверждает ровно один конкретный payload.
- Import apply реально создаёт заметки/индекс; повторный импорт не создаёт дубли.
- Сбой после записи файла устраняется retry/reconcile без потери поиска и дубля.
- Crash в `processing` восстанавливается после истечения lease.
- Повторная индексация одного `note_id` оставляет один результат.
- Relevance принимает одну сильно совпавшую тему независимо от общего числа тем.
- Wheel после установки находит промпты и example resources вне исходного репозитория.
- MCP integration: initialize показывает tools capability; list/call возвращает структурированные данные.
- Prompt injection в заметке не может удалить источник или подтвердить изменение.
- Два параллельных worker не обрабатывают одно задание одновременно.

### Definition of Done для следующего релиза

- Все перечисленные regression-тесты зелёные в CI на поддерживаемых Python 3.10–3.12.
- `ruff`, type checking и build/install wheel проходят.
- Нет статусов `applied`, если фактический объект не изменился.
- Нет необработанных `failed/processing` без способа восстановления.
- `kb-agent reindex` восстанавливает поиск из vault.
- README описывает только проверенное поведение и честную модель передачи данных LLM.
- Scheduled workflow действительно запускает основной конвейер либо отключён.
- MCP read-only режим работает без write/confirm tools; write proposals требуют внешнего подтверждения.
