**Дата:** 14.11.2026 · **Версия:** 0.2.2 · **Объём:** ~40 модулей Python, 35 тестовых файлов, 4 GitHub Actions workflow

**Способ проверки:** чтение исходного кода через GitHub API (raw-файлы). Код не запускался, тесты не выполнялись — это статический обзор.

## 1. Общее впечатление

Зрелый, хорошо организованный проект. Архитектура чистая и слоистая:

```
sources/ (telegram, youtube) → raw_queue (SQLite)
      → Relevance Gate → LLM-суммаризация → vault (Obsidian .md)
      → FTS5-индекс → Каталог.md / Дайджест.md
agents/mcp_server.py — доступ внешних ИИ-агентов (read + pending-write)
```

### Сильные стороны

- **Чёткое разделение ответственности**: `sources` / `processing` / `storage` / `core` / `cli` / `agents`, почти нет циклических связей.
- **Надёжная работа с SQLite**: версионированные миграции (24 шага, включая функциональные), WAL, `busy_timeout`, `BEGIN IMMEDIATE` для конкурентных операций, lease-механизм очереди с экспоненциальным backoff.
- **Идемпотентность на всех уровнях**: дедупликация по `external_id` и `raw_hash`, сохранение `note_id` в очереди для повтора после частичного сбоя, `content_hash` для пропуска неизменённых заметок.
- **Атомарная запись файлов** (`tmp` + `os.replace` + `.bak`) в vault, YAML-экспорте и профиле.
- **Продуманная безопасность MCP**: allowlist хостов источников, write-операции только через pending-запросы с подтверждением человеком, `payload_hash` против подмены параметров, оптимистичная блокировка по `revision`, фильтрация приватных заметок, маскирование секретов в логах.
- **Структурированный вывод LLM** по JSON-схеме с Pydantic-валидацией и повтором при невалидном ответе, circuit breaker, ретраи с джиттером.
- **Качественный CI**: матрица Python 3.10–3.12, ruff, pytest, сборка wheel и smoke-проверка установки, pip-audit, dependabot, pre-commit.
- **Тесты**: 35 файлов, включая безопасность (`test_security_*`), конкурентность lease (`test_lease_concurrency`), prompt injection, миграции.
- **Документация** выше среднего: README на двух языках, architecture.md, SECURITY.md, CHANGELOG.

## 2. Критичные проблемы

### 2.1. 🔴 Утечка приватных данных через артефакты GitHub Actions

**Файл:** `.github/workflows/collect.yml`

Workflow ежедневно запускает конвейер на эфемерном раннере и сохраняет **весь vault и state.db** как артефакт `kb-state`:

```yaml
- name: Сохранить артефакты (vault + state.db)
  uses: actions/upload-artifact@...
  with:
    name: kb-state
    path: |
      ${{ env.KB_VAULT_PATH }}/
      ${{ env.KB_DB_PATH }}
```

В публичном репозитории артефакты доступны для скачивания любому пользователю. То есть вся ваша база знаний (заметки, суммаризации приватных каналов, история обработки) публикуется в виде артефакта. Это прямо противоречит собственной политике проекта (метки `is_private`, фильтрация в MCP) — приватность защищена на уровне API, но сами данные раздаются через CI.

**Рекомендации:**
- Перенести хранение состояния в приватный репозиторий, приватный package registry или зашифрованный артефакт (например, шифрование age/OpenSSL с ключом в Secrets).
- Минимум: делать репозиторий приватным или убрать сохранение vault/state.db в публичном workflow.

### 2.2. 🔴 Секреты записываются в GITHUB_ENV

**Файл:** `.github/workflows/collect.yml`

```yaml
echo "KB_OPENAI_API_KEY=${{ secrets.KB_OPENAI_API_KEY }}" >> $GITHUB_ENV
```

Запись секретов через `GITHUB_ENV` делает их постоянными переменными окружения для **всех** последующих шагов job'а — любой шаг (в том числе сторонний action или отладочный `env`) получает доступ к ключу. Кроме того, при пустом секрете это порождает баг 3.3. GitHub рекомендует передавать секреты через `env:` конкретного шага.

**Рекомендация:**

```yaml
- name: Run kb-agent pipeline
  run: kb-agent process run
  env:
    KB_OPENAI_API_KEY: ${{ secrets.KB_OPENAI_API_KEY }}
```

### 2.3. 🟠 Задокументированные privacy-функции не реализованы в коде

**Файлы:** `kb_agent/config.py`, `kb_agent/processing/llm_client.py`, `kb_agent/processing/pipeline.py`

В конфиге и `.env.example` объявлены `KB_LOCAL_PROCESSING_MODE` (запрет отправки данных внешнему LLM) и `KB_REDACT_FIELDS` / `KB_REDACT_SOURCES` (редакция чувствительных полей). В README это подано как реализованное (раздел 6.2). Однако в `LLMClient.complete()` **нет ни проверки `local_processing_mode` (блокировки внешних провайдеров), ни какой-либо редакции** — сырой текст всегда уходит в `/chat/completions` выбранного провайдера. Тест `test_local_processing_mode_config` проверяет только то, что поле конфига читается, а не поведение.

Пользователь, включивший «локальный режим», будет уверен, что данные не покидают машину, — а они будут уходить на внешний API. Это самый опасный тип расхождения «документация ↔ код».

**Рекомендация:** реализовать в `LLMClient` guard: при `local_processing_mode=True` запрещать провайдеров вне `("ollama", "local")`; добавить редакцию полей перед отправкой; покрыть тестами поведение, а не только чтение конфига.

## 3. Ошибки и баги

### 3.1. Двойной инкремент `attempts` ускоряет backoff вдвое

**Файл:** `kb_agent/storage/state.py`

`claim_next()` инкрементирует `attempts = attempts + 1` при захвате, а `mark_failed()` инкрементирует `attempts = attempts + 1` ещё раз при неудаче. За один цикл обработки `attempts` растёт на 2, поэтому экспоненциальная задержка `min(2**attempts, 24ч)` растёт вдвое быстрее задуманного: после двух реальных попыток delay уже 8 минут вместо 4, после четырёх — 4 часа вместо 16 минут.

**Рекомендация:** инкрементировать `attempts` в одном месте (логично — в `claim_next`), а `mark_failed` оставить только установку `state/last_error/next_retry_at`.

### 3.2. Пустые секреты в CI ломают конфигурацию LLM

**Файл:** `.github/workflows/collect.yml` + `kb_agent/config.py`

Строки `echo "KB_OPENAI_BASE_URL=${{ secrets.KB_OPENAI_BASE_URL }}" >> $GITHUB_ENV` выполняются **безусловно**. Если секрет не задан, в окружение попадает пустая строка, а `load_config()` считает переменную заданной (`if env_name in os.environ`) и подставляет `""` вместо дефолта. Итог: `openai_base_url=""`, `openai_model=""`, запросы уходят на `/chat/completions` без хоста — конвейер падает с невнятной ошибкой.

**Рекомендация:** писать переменную только при непустом секрете (`if [ -n "${{ secrets.X }}" ]; then ... fi`) или передавать через `env:` шага (пустые значения тогда лучше игнорировать и в `load_config` — трактовать пустую строку как «не задано»).

### 3.3. Рассинхрон схемы MCP-инструмента и реализации

**Файл:** `kb_agent/agents/mcp_server.py`

- В `inputSchema` для `kb_search` заявлено `"maximum": 100` для `limit`, код жёстко ограничивает `min(limit, 20)`. Внешний агент, запросивший 50, получит 20 без предупреждения.
- Поле `total` в `SearchOutput` описано как «количество найденных», но фактически это `cursor + len(items) + (1 if has_more)` — не общее число, а приближение. Для клиента, строящего пагинацию по `total`, это источник ошибок.

**Рекомендация:** либо честный `COUNT(*)` по FTS-запросу (дёшево на личных объёмах), либо переименовать поле (`has_more` / `returned`) и синхронизировать максимум.

### 3.4. Утечка соединений в MCP-сервере

**Файл:** `kb_agent/agents/mcp_server.py`, `handle_call_tool`

На каждый вызов инструмента создаются `load_config()` + `StateManager` + `LLMClient`, вызывается `state.init_db()` (полный проход по миграциям), но `state.close()` нигде не вызывается — соединения закрываются только сборщиком мусора. При длинной сессии MCP-агента соединения и WAL-файлы накапливаются.

**Рекомендация:** кэшировать `StateManager`/`LLMClient` на уровне процесса (создавать лениво один раз) или оборачивать обработку в `try/finally` с `close()`.

### 3.5. `check_duplicates` без сортировки — недетерминированный результат

**Файл:** `kb_agent/core/update.py`

Запрос `JOIN ... WHERE n1.tags = n2.tags ... LIMIT ?` без `ORDER BY` возвращает произвольные пары. Плюс критерий «одинаковые теги = дубликат» даёт много ложных срабатываний (все заметки про одну тему помечаются как возможные дубли).

**Рекомендация:** добавить `ORDER BY` (например, по длине общих тегов или дате) и ужесточить критерий (совпадение тегов + похожесть заголовков, либо нормализованная схожесть текста).

### 3.6. Мелкие замечания по коду

- `kb_agent/sources/youtube.py`: сообщение об ошибке советует `pip install '.[youtube]'`, но extra `youtube` в `pyproject.toml` не существует (yt-dlp и так в основных зависимостях) — введёт пользователя в заблуждение.
- `kb_agent/processing/llm_client.py`, `_extract_json_block`: regex `\{.*?\}` с `re.DOTALL` корректно обрабатывает вложенные скобки только пока внутри нет последовательности `}` + ```` ``` ````; надёжнее валидировать распарсенность и при неудаче падать на fallback «от первой `{` до последней `}`» (сейчас fallback недостижим, если regex что-то совпал).
- `kb_agent/core/search.py`, `_make_snippet`: конструкция `return snippet, (0, len(snippet)) if snippet else None` работает из-за приоритета операторов, но читается как «вернуть tuple либо None». Стоит явно взять в скобки.
- `kb_agent/storage/pending.py`, `_update_profile`: используется `yaml.dump` (не `safe_dump`) — во всём остальном коде применяется `safe_dump`; лучше унифицировать.
- `kb_agent/config.py`: `PROJECT_ROOT` определяется по наличию `pyproject.toml` в CWD — если пользователь запустит CLI в случайной папке с чужим `pyproject.toml`, данные уйдут не туда. Надёжнее опираться на расположение `__file__` в первую очередь.
- `kb_agent/utils/spam.py`: подстрочный поиск `купи`, `скидка`, `реклама` даёт ложные срабатывания на легитимных постах («как купить квартиру» уходит в спам). Как минимум логировать причину в `skipped_reason`, чтобы можно было вернуть через `kb-agent retry`.
- `kb_agent/processing/pipeline.py`, `_process_queue`: при открытом circuit breaker каждый элемент очереди быстро помечается `failed` с растущим backoff — данные не теряются, но прогон «сгорает» целиком. Можно останавливать цикл при открытом circuit breaker и оставлять элементы в `new`.

## 4. Качество CI/CD

### 4.1. mypy и pip-audit не блокируют merge

**Файл:** `.github/workflows/ci.yml`

```yaml
- run: mypy kb_agent || true
...
- run: pip-audit ... || true
```

Обе проверки декоративные: `|| true` гарантирует зелёный CI при любых находках. При этом `pyproject.toml` содержит строгую конфигурацию mypy (`disallow_untyped_defs` и т.д.) — она фактически не используется как gate.

**Рекомендация:** зафиксировать текущий baseline (например, `mypy kb_agent | tee mypy.txt`, падать при росте числа ошибок) и убрать `|| true` у pip-audit, добавив подавление известных ложных срабатываний через `--ignore-vuln`.

### 4.2. Непоследовательное закрепление версий actions

В `collect.yml` actions закреплены по SHA (хорошая практика), в `ci.yml` — по тегам `@v4`/`@v5`. Dependabot обновляет оба, но для supply-chain-гигиены стоит унифицировать по SHA.

### 4.3. Ретеншн артефактов состояния

Артефакт `kb-state` хранится 90 дней по умолчанию; после 90 дней безуспешных запусков база «обнуляется» и конвейер начнёт собирать всё заново (частично спасает дедупликация по external_id, но vault с заметками будет потерян). Стоит задать `retention-days` явно и продумать внешний бэкап (см. 2.1).

## 5. Гигиена репозитория

- **Три файла аудита в корне**: `AUDIT_REPORT.md`, `AUDIT_REPORT_FINAL.md`, `5AUDIT_REPORT.md` (~107 КБ суммарно) плюс `docs/history/` с ещё шестью историческими документами. Корень стоит почистить: рабочие аудиты перенести в `docs/`, историю — в `docs/history/` (или удалить, история есть в git).
- **Артефакты ИИ-генерации в комментариях**: в `kb_agent/sources/registry.py` встречаются фрагменты на корейском (`# ---- 내부: ...`, `# ---- Запись (할я SQLite канонически) ----`), в `kb_agent/storage/pending.py` — обрывок «confirmaцияremaining», в `state.py` — опечатка «Атоматически», в `youtube.py` — «Если бинарный файл absent». Это мелочь, но такие артефакты снижают доверие при чтении кода и выдают места, где текст не вычитывался.
- `SKILL.md` и `.cursorrules` в корне — специфика ИИ-инструментов; лучше собрать в отдельный каталог, если они нужны нескольким агентам.
- Дублирование ресурсов: `config/prompts/*` и `kb_agent/resources/prompts/*` (осознанно, для wheel, и CI проверяет синхронность — хорошо, но можно генерировать одно из другого при сборке).

## 6. Безопасность: что сделано хорошо

Отдельно отмечу удачные решения, которые редко встречаются в личных проектах:

1. **Pending-confirm для всех write-операций MCP** — внешний агент физически не может изменить источники/профиль/промпты без подтверждения человеком через CLI.
2. **`payload_hash` + `revision`** — защита от TOCTOU-подмены параметров между созданием и подтверждением предложения.
3. **Allowlist хостов** для добавляемых источников (t.me/youtube.com), включая проверку схемы и суффиксов доменов.
4. **Маскирование секретов в логах** (`SecretFilter` с паттернами sk-*, JWT, password=...) + rotating file handler.
5. **Тесты на prompt injection и path traversal** (`test_prompt_injection.py`, `test_security_config.py` с проверкой `../` в путях).
6. `httpx` без `trust_env` для LLM-вызовов снижает поверхность SSRF через прокси-переменные (хотя и ломает работу за корпоративным прокси — задокументируйте).

Оставшаяся главная дыра — не в коде, а в инфраструктуре (пункты 2.1–2.3).
