## Аннотация

Данный отчет содержит результаты полного аудита репозитория `personal-kb-agent` — личного ИИ-агента для базы знаний с поддержкой Telegram, YouTube, Obsidian и MCP. Аудит охватывает структуру репозитория, документацию, код, безопасность, конфигурацию, тестирование, упаковку и лингвистические аспекты.

**Общая оценка:** Проект качественно реализован, имеет продуманную архитектуру, хорошее покрытие тестами (297 тестов), соответствует современным практикам разработки на Python. Выявлены ряд проблем разной степени критичности, которые рекомендуется устранить для повышения надежности, удобства поддержки и профессионального вида проекта.

В CHANGELOG указано "yt-dlp перенесен в основные зависимости, убрана верхняя граница версии" — это правильно, так как yt-dlp часто обновляется для поддержки YouTube.

### 3.2 config.py — анализ качества

**Сильные стороны:**
- Продуманная система приоритетов загрузки конфига
- Валидация через Pydantic v2
- Поддержка упакованных ресурсов (wheel) и режима разработки

**Проблемы:**

#### 3.2.1 `PROJECT_ROOT` вычисляется некорректно при установке в wheel
Строки 27, 35-36: `PROJECT_ROOT = Path(__file__).resolve().parent.parent` — при установке через `pip install .` (wheel) `__file__` указывает в `site-packages/kb_agent/config.py`, поэтому `PROJECT_ROOT` будет `site-packages/kb_agent/../..` = `site-packages/`. Это ломает fallback-пути для промптов и конфигов.

**Рекомендация:** Использовать `importlib.resources` для ресурсов пакета, а для пользовательских данных — только `KB_DATA_DIR` / `data_dir`. Убрать зависимость от `PROJECT_ROOT` для путей по умолчанию.

#### 3.2.2 `DEFAULT_PROMPTS_DIR = PROJECT_ROOT / "config" / "prompts"` — не работает в wheel
В �ле папки `config/` нет. Нужно полагаться только на `kb_agent.resources` (importlib.resources).

#### 3.2.3 Дублирование логики путей
В `_resolve_paths()` и в `load_config()` — логика разрешения путей разбросана. Стоит консолидировать.

#### 3.2.4 Отсутствует валидация `llm_provider`
Допустимые значения документированы только в комментарии и .env.example. Стоит добавить `Literal["openai", "kimi", "anthropic", "ollama", "openrouter", "custom"]` или Enum.

### 4.2 Критические и высокие риски в коде

#### 4.2.1 SQL-инъекция в `StateManager.rebuild_fts()` (строка 1052-1058)
```python
cur = conn.execute(
    """
    INSERT INTO notes_fts (note_id, title, tags, topic, content)
    SELECT note_id, title, tags, topic, content_hash  -- БАГ: content_hash вместо content!
    FROM notes
    """
)
```
**БАГ:** Вставляется `content_hash` вместо `content`! FTS5 индексирует хеш, а не текст заметки. Поиск не будет работать корректно.

**Исправление:** Заменить `content_hash` на `content`.

#### 4.2.2 SQL-инъекция в `StateManager.search()` (строка 1129)
```python
f"""
SELECT ... FROM notes_fts f LEFT JOIN notes n ON n.note_id = f.note_id
{where_clause}
ORDER BY rank LIMIT ? OFFSET ?
""",
```
`where_clause` формируется через f-string с интерполяцией условий. Хотя условия строятся из проверенных параметров, это антипаттерн. Лучше использовать параметризованные запросы полностью.

**Рекомендация:** Переписать на безопасное построение запроса через список условий и параметров.

#### 4.2.3 Отсутствие таймаута на уровне httpx в Telegram-сборщике
`kb_agent/sources/telegram.py` строка 63: `with httpx.Client(timeout=20) as client:` — таймаут только на запрос, нет таймаута на соединение (`connect_timeout`). При проблемах с DNS/TCP может висеть долго.

**Рекомендация:** `httpx.Client(timeout=httpx.Timeout(connect=10.0, read=20.0, write=10.0, pool=5.0))`

#### 4.2.4 Уязвимость path traversal в `VaultManager.find_note_file()`
Строки 58-72: перебирает все файлы через `rglob("*.md")` и парсит frontmatter. Если злоумышленник положит в vault файл с `../../../etc/passwd` в frontmatter `note_id` — не критично, но при чтении `parse_note` использует `path.read_text()`. Пути контролируются vault'ом, риск минимален, но лучше валидировать, что путь внутри `vault_path`.

#### 4.2.5 `subprocess.run` с `shell=False` (хорошо), но без валидации аргументов в youtube.py
Строки 44-53, 133-144: аргументы yt-dlp формируются из пользовательского ввода (`channel_url`, `video_url`). Хотя yt-dlp валидирует URL, лучше добавить явную проверку, что URL принадлежит youtube.com/youtu.be.

#### 4.2.6 Race condition в `StateManager.claim_next()`
Строки 585-625: использует `BEGIN IMMEDIATE` — хорошо для SQLite. Но `lease_expires_at` устанавливается после SELECT. Если процесс упадет между SELECT и UPDATE — lease не установится, элемент останется в `new`. Это правильно (безопасно), но стоит добавить комментарий.

### 4.3 Баги и логические ошибки

#### 4.3.1 `rebuild_fts()` — неверное поле (см. 4.2.1)

#### 4.3.2 `VaultManager.parse_note()` строка 372: `content_hash` считается от `body.strip()`, а в `index_note()` (state.py:317) — от `content` (который уже без frontmatter). При переиндексации через `reindex` (process.py:216) используется `parsed["content_hash"]`, который считается в `parse_note`. Но при обычной индексации в pipeline (pipeline.py:317) считается отдельно. **Несоответствие алгоритмов хеширования** — при reindex хеши будут отличаться, что заставит перезаписывать заметки при следующем запуске.

**Рекомендация:** Унифицировать расчет `content_hash` в одном месте (утилита).

#### 4.3.3 `VaultManager._sanitize_frontmatter()` (строки 293-325) — эвристика, которая может сломать валидный YAML
Пытается "починить" значения, начинающиеся с `@`, содержащие `: ` и т.д. Но `yaml.safe_load` уже корректно парсит закавыченные строки. Эта функция может сломать легальные значения (например, `"user@example.com"` станет `'"user@example.com"'`).

**Рекомендация:** Убрать эту функцию и полагаться на `yaml.safe_dump` при записи (что уже делается). При чтении — просто `yaml.safe_load`, ошибки логировать.

#### 4.3.4 `Pipeline._process_queue()` строка 233: `source_type = item["source_id"].split("_")[0]` — хрупкая привязка к префиксу `tg_`/`yt_`. Если изменится схема именования source_id — сломается.

**Рекомендация:** Хранить `source_type` в `raw_queue` или получать из реестра источников.

#### 4.3.5 `RelevanceGate._tokens()` использует regex `[а-яёa-z0-9]{2,}` — исключает однобуквенные токены, но в русском языке важные слова могут быть однобуквенными (предлоги уже в stop_words, но частицы "б", "ль" — тоже в stop_words). Нормально, но стоит документировать.

#### 4.3.6 `SPAM_PATTERNS` в relevance.py (строка 222-225) дублирует `SPAM_KEYWORDS` в telegram.py (строки 24-38). Несоответствие: в telegram.py проверка простая `kw in lower`, в relevance.py — regex с границами слов. Результаты могут отличаться.

**Рекомендация:** Вынести спам-фильтр в общий модуль `kb_agent/core/spam.py`.

### 5.2 Проблемы безопасности

#### 5.2.1 API-ключ в логах
В `LLMClient` (не читал, но стандартная проблема) — при логировании запросов/ответов может попасть `Authorization: Bearer sk-...`. Проверить, что логгер маскирует ключи.

#### 5.2.2 `.env` файл в .gitignore есть, но нет проверки в коде
При запуске без `.env` — падает с непонятной ошибкой. Стоит добавить понятное сообщение: "Создайте .env из .env.example".

#### 5.2.3 `yt-dlp` выполняет внешние запросы
Ограничение доменов через `--match-filter` и allowlist в MCP есть, но при прямом вызове `kb-agent process run` — yt-dlp может ходить куда угодно. Стоит добавить прокси или firewall на уровне ОС/контейнера для изоляции.

#### 5.2.4 `subprocess.run` с `timeout` — есть, но нет ограничения ресурсов (CPU, память)
Для yt-dlp — нормально, но в контейнере стоит лимитировать.

#### 5.2.5 Отсутствует `SECURITY.md` с политикой раскрытия уязвимостей
Рекомендуется добавить для open source проекта.

## 7. Упаковка и распространение

### 7.1 Проблемы с wheel/sdist

1. **Ресурсы не упаковываются корректно:**
   В `pyproject.toml`:
   ```toml
   [tool.setuptools.package-data]
   kb_agent = ["resources/**/*"]
   ```
   Но в исходниках ресурсы лежат в `config/prompts/`, `config/sources.example.yaml`, `config/user_profile.example.yaml`. При установке через `pip install .` они не попадут в wheel, так как не входят в пакет `kb_agent`.

   В `config.py` (строки 29-30): `RESOURCES_PACKAGE = "kb_agent.resources"` — ожидает ресурсы внутри пакета. Нужно перенести ресурсы в `kb_agent/resources/` или изменить стратегию упаковки.

2. **`config/sources.example.yaml` и `config/user_profile.example.yaml`** — не упакованы, но используются как fallback. В wheel их не будет.

**Рекомендация:** 
- Создать `kb_agent/resources/` с подпапками `prompts/`, `config/`
- Перенести туда все шаблоны
- Обновить `config.py` для чтения оттуда
- В режиме разработки fallback на `config/` оставить

### 7.2 Отсутствие публикации в PyPI

Проект не опубликован в PyPI. Для пользователей установка только через `pip install -e .` из исходников.

**Рекомендация:** Настроить публикацию в PyPI через GitHub Actions (trusted publishing).

### 7.3 Версионирование

Hardcoded версия в `pyproject.toml`. Рекомендуется `setuptools_scm` или `hatch_vcs`.

## 10. Заключение

Проект **personal-kb-agent** представляет собой качественно реализованный, архитектурно продуманный инструмент для личной базы знаний с современным стеком (Python 3.10+, SQLite FTS5, MCP, Pydantic v2). Код читаем, покрыт тестами (297 тестов), документирован.

**Главные риски:**
1. Баг в `rebuild_fts()` делает полнотекстовый поиск неработоспособным после переиндексации
2. Артефакты сборки в репозитории — признак отсутствия CI/CD
3. Ресурсы не упаковываются в wheel — проект не устанавливается через `pip install personal-kb-agent`

**После устранения критических проблем** проект готов к публикации в PyPI и использованию сообществом.
