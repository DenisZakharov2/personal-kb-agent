## 🎯 Что это и зачем нужно

### Проблема, которую решает kb-agent

Ежедневно получаете поток полезной информации из Telegram-каналов, YouTube, сайтов и своих файлов. Часть материалов теряется, часть забывается, а связей между разными источниками почти не остаётся. Чтобы найти нужную мысль, приходится перечитывать десятки постов вручную.

**kb-agent** решает эту проблему: он автоматически собирает материалы из выбранных вами источников, суммаризирует их через LLM и сохраняет структурированные заметки в ваш Obsidian vault. Заметки получают теги, темы и ссылку на источник; связи между заметками хранятся в таблице `note_links`. Все заметки проиндексированы и доступны для поиска — как вам, так и любому ИИ-агенту (Cursor, Claude Code, Hermes, OpenCode и др.).

## 💡 Что вы получаете

### Для человека (пользователя Obsidian / KB)

| Выгода | Как это работает |
|--------|------------------|
| **Ничего не теряется** | Пост или видео попадает в очередь → relevance-фильтрация → суммаризация → заметка в vault (неподходящие или необрабатываемые материалы пропускаются) |
| **Видеть связи между источниками** | Заметки получают теги, темы и ссылку на исходный материал; связи между заметками хранятся в таблице `note_links` |
| **Быстро находить нужное** | Полнотекстовый поиск (FTS5) по всем заметкам + команда `kb-agent ask` |
| **Получать инсайты без усилий** | Агент находит повторяющиеся темы и связи между заметками (по общим тегам, топ-3) |
| **Управлять потоком информации** | Добавляйте/удаляйте источники одной командой, без правки кода |
| **Контроль качества** | Оцените каждую заметку (1–5), агент подстроится под ваши предпочтения |

### Для ИИ-агентов (Cursor, Claude Code, Hermes, OpenCode, Kimi Claw и др.)

| Выгода | Как это работает |
|--------|------------------|
| **Чтение вашей базы знаний** | MCP-сервер `kb-agent mcp-serve` даёт инструменты `kb_search`, `kb_get_note`, `kb_get_insights` |
| **Поиск по вашим заметкам** | FTS5-поиск через `kb_search` |
| **Получение инсайтов** | `kb_get_insights` возвращает связи между заметками |
| **Настройка без кода** | Write-инструменты (`kb_add_source`, `kb_remove_source`, `kb_enable_source`, `kb_update_profile`, `kb_revert_prompt`) создают pending-запрос, который применяется только после явного человеческого подтверждения через `kb-agent confirm <id>` |

## 🚀 Быстрый старт

### 1. Установка

```bash
# Клонируйте репозиторий
git clone https://github.com/DenisZakharov2/personal-kb-agent.git
cd personal-kb-agent

# Установите зависимости (включая yt-dlp для YouTube)
pip install -e .

# Проверьте установку
kb-agent --version
```

### 2. Настройка (.env)

```bash
cp .env.example .env
# Отредактируйте .env — укажите путь к vault, каналы, ключ LLM
```

| Переменная | Что указать | Пример |
|------------|-------------|--------|
| `KB_VAULT_PATH` | Путь к вашему Obsidian vault | `/home/user/Documents/KB` |
| `KB_TELEGRAM_CHANNELS` | Каналы Telegram через запятую | `ragnarokzone,paragonzone,rubiconzone` |
| `KB_YOUTUBE_CHANNELS` | YouTube каналы (полные URL) | `https://youtube.com/@amorev,https://youtube.com/@rubiconzone` |
| `KB_LLM_PROVIDER` | Провайдер LLM | `openai`, `kimi`, `ollama`, `openrouter` |
| `KB_OPENAI_API_KEY` | Ваш API-ключ | `sk-...` |
| `KB_OPENAI_BASE_URL` | URL API провайдера | `https://api.openai.com/v1` |

### 3. Первое интервью (обязательно перед стартом)

```bash
kb-agent interview init
```

Агент задаст несколько вопросов о целях, темах, источниках и частоте сбора — и создаст ваш `user_profile.yaml`.

### 4. Запуск конвейера

```bash
# Собрать материалы из всех источников и суммаризировать в vault
kb-agent process run

# Или получить дайджест запуска
kb-agent process digest
```

#### Коды выхода `kb-agent process run` (P2-14)

| Код | Значение | Когда возвращается |
|-----|----------|--------------------|
| `0` | Успех | Все источники собраны без ошибок, обработка очереди прошла без сбоев |
| `1` | Ошибка сбора/обработки | Есть хоть одна ошибка сбора источника или обработки очереди (partial success считается ошибкой) |
| `2` | Критическая ошибка конфигурации | Не удалось загрузить конфигурацию (нет профиля, некорректные пути и т.д.) |

При любом сбое CLI печатает блок **Ошибки сбора источников:** с `source_id` и текстом ошибки для каждого упавшего источника, а при `processing_failed > 0` — отдельный блок **Ошибок обработки очереди**. JSON-вывод (`--json`) содержит секции `health` (статус каждого источника) и `summary` (итоги).

### 5. Работа с базой знаний

```bash
# Задать вопрос и получить ответ со ссылками на заметки
kb-agent ask "Что я накопил по теме ИИ-агентов?"

# Поиск заметок (список)
kb-agent search "автоматизация n8n"

# Инсайты — связи между заметками (таблица note_links)
kb-agent insights

# Проверка на дубликаты
kb-agent update check
```

### 6. Управление источниками

```bash
# Список всех источников
kb-agent sources list

# Добавить канал Telegram
kb-agent sources add telegram https://t.me/s/novyikanal

# Добавить YouTube канал
kb-agent sources add youtube https://youtube.com/@novyykanal

# Включить/выключить источник
kb-agent sources enable tg_ragnarokzone
kb-agent sources disable yt_staryykanal

# Удалить источник
kb-agent sources remove tg_staryykanal
```

> ⚠️ Команды `kb-agent sources ...` пишут в каноническое хранилище источников (SQLite). Изменения, пришедшие из MCP-инструментов (агент), создают pending-запрос — его нужно подтвердить командой `kb-agent confirm <id>`.

### 7. MCP-сервер для AI-агентов

```bash
# Запустить сервер (один раз, в терминале или как сервис)
kb-agent mcp-serve
```

Подключите в вашем AI-агенте (например, в `.cursor/mcp.json`):

```json
{
  "mcpServers": {
    "kb-agent": {
      "command": "kb-agent",
      "args": ["mcp-serve"]
    }
  }
}
```

Теперь ваш агент может:
- Искать по вашим заметкам: `kb_search("ИИ-агенты")`
- Читать содержимое заметки: `kb_get_note("note_id")`
- Получать инсайты: `kb_get_insights()`
- Предлагать изменения источников и профиля: `kb_add_source(...)` → подтверждение через `kb-agent confirm <change_id>`

## 🔄 Как конвейер работает под капотом

1. **Сбор** — новые посты из Telegram и видео из YouTube попадают в `raw_queue`
2. **Relevance Gate** — материал проверяется на соответствие вашим целям и темам из профиля
3. **Суммаризация** — LLM перестраивает сырой текст в структурированную заметку (суть, идеи, инструменты, выводы, теги)
4. **Запись** — заметка сохраняется в тематическую папку vault с YAML frontmatter
5. **Индексация** — заметка добавляется в FTS5-индекс для поиска
6. **Каталог** — `Каталог.md` пересобирается автоматически
7. **Дайджест** — `Дайджест.md` в vault со статистикой запуска

## 🔐 Безопасность и приватность

### Модель передачи данных внешнему LLM (6.2)

Заметки, база состояния и профиль хранятся локально на вашем компьютере.
Однако **сырые тексты, найденные заметки и метаданные отправляются настроенному
внешнему OpenAI-совместимому endpoint** (OpenAI, Kimi, OpenRouter, Ollama и др.)
для суммаризации и поисковых ответов:

| Что отправляется | Кому | Когда |
|------------------|------|-------|
| Сырой текст поста/видео (`raw_text`) | Настроенный LLM-провайдер (`KB_OPENAI_BASE_URL`) | При суммаризации в конвейере (`kb-agent process run`) |
| Фрагменты заметок (snippets) + метаданные (ID,タイトル, теги, URL источника) | Настроенный LLM-провайдер | При поисковых ответах (`kb-agent ask`, `kb_search` через MCP) |
| Метаданные источников (source_id, channel, canonical_url) | Настроенный LLM-провайдер | При суммаризации и поиске |
| API-ключ (`KB_OPENAI_API_KEY`) | Внешний провайдер (только если не Ollama/локальный) | Каждый запрос к LLM |

Если важна полная локальность, используйте локального провайдера (Ollama) без
API-ключа и включите режим локальной обработки (см. ниже).

### Режим локальной обработки (6.2)

Переменная `KB_LOCAL_PROCESSING_MODE=true` включает режим, при котором данные
не отправляются внешнему LLM-провайдеру. Работает только с локальным Ollama/
локальной моделью. Внешние провайдеры (OpenAI, Kimi, OpenRouter) блокируются.

```bash
export KB_LOCAL_PROCESSING_MODE=true
kb-agent process run
```

### Redaction — исключение чувствительных данных (6.2)

Переменные `KB_REDACT_FIELDS` и `KB_REDACT_SOURCES` позволяют исключить
чувствительные поля и источники из отправки внешнему LLM:

```bash
# Исключить поля email, phone, URL источников из отправки LLM
export KB_REDACT_FIELDS="email,phone,canonical_url"

# Исключить весь контент отдельных источников
export KB_REDACT_SOURCES="tg_private_chan,yt_internal_channel"
```

### Метки чувствительности в MCP (6.2)

Заметки и источники можно помечать как приватные (`is_private = 1`).
Приватные заметки **не возвращаются** внешнему агенту через `kb_get_note` и
фильтруются из результатов `kb_search` для внешнего MCP-клиента. Чувствительность
отмечается полями `is_private` и `sensitivity` (public/internal/private/secret)
в структурированном ответе MCP.

### Цепочка недоверенного контента и действий агента (6.1)

- **Нет confirm-инструмента в MCP.** Модель не может подтвердить изменение
  самостоятельно. Подтверждение человека — только через отдельный CLI-канал:
  `kb-agent confirm <id>` (или `kb-agent confirm <id> --revision N`).
- **Write-инструменты MCP** (`kb_add_source`, `kb_remove_source`,
  `kb_enable_source`, `kb_update_profile`, `kb_revert_prompt`) создают
  pending-предложение, но не применяют его. Применение требует человеческого
  подтверждения через CLI.
- **Каждое pending-предложение содержит:** diff, payload_hash, base_revision,
  автора (created_by), время истечения (TTL/expires_at), одноразовый
  идентификатор (change_id).
- **При подтверждении атомарно проверяются:** status='pending', payload_hash
  (параметры не подменялись), актуальная ревизия объекта.
- **Мета-данные происхождения** каждого фрагмента (URL, source, note_id,
  метка `untrusted_content`) включаются в MCP-ответы (`kb_search`,
  `kb_get_note`).
- **Allowlist источников и URL:** при добавлении источника через MCP хост
  валидируется против allowlist доверенных доменов (t.me, youtube.com,
  youtu.be и т.д.). yt-dlp ограничен известными YouTube-доменами.
- **Защита от prompt injection:** модель не имеет инструментов прямой записи.
  Вредоносный текст в заметке не может привести к удалению источника или
  изменению профиля — только к созданию pending-предложения, которое требует
  отдельного человеческого подтверждения.

### Опасный latent API записи конфигурации (6.3)

`apply_config_proposal` ограничен строгим allowlist конфигурационных файлов,
выполняет атомарную запись (temp-файл + os.replace) и проверяет diff перед
записью. Попытка записи вне allowlist отклоняется.

## 📊 Обратная связь и самоулучшение

```bash
# Оценить заметку (1–5)
kb-agent feedback rate <note_id> 5 --comment "Отличная суммаризация"

# Оставить произвольное сообщение
kb-agent feedback tell "Нужно больше примеров кода"

# Посмотреть метрики качества
kb-agent feedback metrics

# Посмотреть предложения по улучшению промптов
```bash
kb-agent self-improve
```

## Самоулучшение (self-improve)

Все подкоманды поддерживают флаг `--json` (`-j`) для машинного вывода.

```bash
# Показать метрики обратной связи и список предложений
kb-agent self-improve

# Список предложений (по умолчанию со статусом proposed)
kb-agent self-improve list
kb-agent self-improve list --status proposed
kb-agent self-improve list --status rejected --json

# Предложить изменение промпта
kb-agent self-improve propose-prompt agent_prompt "нужна ясность суммаризации" "новый текст промпта"
# либо содержимое из файла:
kb-agent self-improve propose-prompt agent_prompt "причина" --content-file prompts/new_agent_prompt.md

# Применить предложение промпта (требует проверки тестовым набором и подтверждения)
kb-agent self-improve apply-prompt <proposal_id> "итоговый текст промпта"
kb-agent self-improve apply-prompt <proposal_id> --content-file prompts/final.md --confirmed-by user

# Отклонить предложение
kb-agent self-improve reject <proposal_id>

# Предложить изменение конфигурации
kb-agent self-improve propose-config data/sources.yaml "старое" "новое" "причина"

# Применить предложение конфига
kb-agent self-improve apply-config <proposal_id> "итоговое значение"

# Откатить промпт к версии
kb-agent self-improve rollback agent_prompt 1
```

Предложения хранятся в SQLite (`prompt_proposals`) и проходят путь:
`proposed → confirmed → applied/rejected/failed`.

Применение промпта и конфига требует проверки изменения на тестовом наборе
(`tests/eval_set.json`) и явного подтверждения пользователя — изменения не
применяются автоматически. Откат промпта (`rollback`) тоже требует
подтверждения.

Агент собирает ваши оценки (`kb-agent feedback rate/tell`) и считает среднюю
оценку. Автоматические предложения по улучшению формируются на основе накопленной
обратной связи.
